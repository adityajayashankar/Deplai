# Deplai Profile Section — Full UI/UX + Functional Provisioning Prompt

## Objective

Provision a complete, production-ready **Profile** section inside Deplai based on the supplied reference screenshots.

This provisioning must cover both:

1. **Functional implementation** — routing, state, APIs, persistence, billing, integrations, security, and account actions.
2. **UI/UX implementation** — visual fidelity, component hierarchy, responsive layouts, interaction states, animations, accessibility, empty states, loading states, error states, dialogs, toasts, and design-system integration.

The result must feel like a native Deplai product surface rather than a standalone settings page.

---

# 1. Critical Navigation Requirement

This is a hard requirement.

When the user clicks:

* `Profile`
* `Your Profile`
* The user/account area in the sidebar

the application must navigate to the Profile screen.

Preferred route:

```text
/profile
```

The Profile route must:

* Render inside the existing Deplai application shell.
* Preserve the existing sidebar/header.
* Mark `Your Profile` as active.
* Open at the top of the Profile page.
* Work with browser Back/Forward.
* Work on direct URL navigation.
* Work after browser refresh.
* Not open as a modal unless the application's existing architecture specifically requires it.
* Never be intercepted by another navigation handler.

# 26. UI Animation & Motion

Use subtle production-quality transitions.

Recommended:

* Card hover: 120–180ms.
* Button hover/press: 100–150ms.
* Tabs/segmented control: 150–220ms.
* Modal enter/exit: 150–220ms.
* Toast: short slide/fade.
* Loading indicators: application-standard animation.

Avoid:

* Excessive bouncing.
* Large page transitions.
* Decorative animation.
* Animation that delays task completion.

Respect:

```text
prefers-reduced-motion
```

# 35. Backend/UI State Contract

Every UI state must map to a real application state.

Do not create UI-only fake states that imply backend success.

Examples:

```text

Payment success → confirmed backend/payment result
Promo success → confirmed redemption
Token reset → confirmed token rotation
Routing saved → confirmed persisted configuration
Account deleted → confirmed deletion workflow started
```

# 36. Security UI Requirements

The UI must treat secrets as sensitive.

Never:

* Display API keys by default.
* Put API keys in logs.
* Put API keys in analytics events.
* Include tokens in toast messages.
* Persist secrets unnecessarily in localStorage.
* Render secrets into unrelated components.

For destructive/security-sensitive operations, use explicit confirmation patterns.
