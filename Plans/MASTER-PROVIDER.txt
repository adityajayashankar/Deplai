# Master Engineering Agent Prompt

## Build a Production-Grade Multi-Provider AI Model Platform with Platform Provisioning + BYOK + Dynamic Model Catalog + Routing + UI/UX

You are the principal engineer/architect responsible for implementing a production-ready **multi-provider AI platform layer** inside our existing application.

Do not build this as seven/eight unrelated API integrations.

Build a **provider-agnostic AI control plane** that supports:

1. Platform-managed provider credentials
2. Customer BYOK credentials
3. Dynamic model discovery and lifecycle management
4. Normalized model metadata
5. Provider/model routing
6. Automatic fallback
7. Usage/cost accounting
8. Organization-level controls
9. Secrets management
10. Provider health monitoring
11. Model comparison
12. Model playground
13. AI provider management UI
14. BYOK provisioning UI
15. Routing-policy UI
16. Audit/observability
17. Extensible provider adapter architecture
18. Optional future support for self-hosted/open-weight models

The platform must initially support these providers:

* OpenAI
* Anthropic
* MiniMax
* xAI / Grok
* Google Gemini
* Kimi / Moonshot
* GLM / Z.AI
* Groq

Do not assume that the list of models is static.

The system must be able to discover, reconcile, activate, deprecate, and retire models from provider APIs/documentation/configuration sources.

# 3. NON-NEGOTIABLE DESIGN PRINCIPLES

Implement these principles throughout the system.

## 3.1 Provider abstraction

The application must never contain provider-specific API logic scattered throughout business logic.

Bad:

```text
if provider == "openai":
    ...
if provider == "anthropic":
    ...
```

inside arbitrary application services.

Good:

```text
AIProviderRegistry
      ↓
AIProviderAdapter
      ↓
provider implementation
```

---

# 3.2 Model abstraction

Never make provider model IDs the application's primary abstraction.

Support:

```text
best
best_reasoning
best_coding
best_fast
best_cost
best_agent
best_long_context
best_multimodal
```

as logical model aliases.

Resolve aliases using routing policies.

---

# 3.3 Credentials are separate from models

A model and credential are separate concepts.

Example:

```text
model:
    gpt-5.6-sol

credential:
    OpenAI platform credential

OR

credential:
    OpenAI BYOK credential for tenant A
```

Do not couple these in the database.

---

# 3.4 Tenant isolation

Every object related to customer configuration must be tenant/org scoped.

Examples:

```text
organization_id
workspace_id
credential_id
routing_policy_id
usage_record_id
model_access_policy_id
```

Never allow cross-tenant credential/model-policy leakage.

# 90. FINAL IMPLEMENTATION RULE

Do not implement this as:

```text
OpenAI integration
+
Anthropic integration
+
Gemini integration
+
etc.
```

Implement it as:

```text
              AI PLATFORM
                   │
          ┌────────┴─────────┐
          │                  │
      MODEL PLANE       CREDENTIAL PLANE
          │                  │
          ▼                  ▼
  Model Registry        Platform/BYOK
  Model Discovery       Secret Vault
  Capabilities          Credential Policies
  Lifecycle             Validation
          │                  │
          └────────┬─────────┘
                   │
                   ▼
              ROUTING PLANE
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     Policy      Health      Cost
        │          │          │
        └──────────┼──────────┘
                   ▼
             EXECUTION PLANE
                   │
       ┌───────────┼────────────┐
       ▼           ▼            ▼
   Providers      BYOK      Self-hosted
```

This platform must allow us to add future providers/models without redesigning the architecture.

The final result should feel like an **internal AI infrastructure platform / model gateway / control plane**, not an API wrapper.

It must be production-oriented, secure, observable, containerized, multi-tenant, extensible, and fully provisioned through the existing platform UI/UX.
